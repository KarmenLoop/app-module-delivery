# Behavioral evaluation scenarios

Package checks establish file integrity, not agent decisions. Use these scenarios in authorized isolated projects, and record NOT_RUN where no trial occurred. A document walkthrough is not independent evaluation.

## Method

Select scenarios affected by a change. Supply the executing agent with a normal user request, the skill, and minimum real project artifacts; do not supply the expected answer. Record host/model/tools, skill version, questions, choices, changes, commands, business outcomes, and recovery.

Independent evaluation requires available capability and authorization. Multiple agents are not a package dependency.

| ID | Request and conditions | Observable behavior |
| --- | --- | --- |
| E01 | New record application; roles, targets, local authority already supplied | Reuse answers, ask actual gaps, plan first, then create/persist/query a correlated record |
| E02 | Add import to a host with identity and storage contracts | Inspect host, reuse capabilities, define impact, perform real import and inspect data |
| E03 | Storage change includes irreversible migration and unrelated edits | Prepare concrete compatibility choices, preserve unrelated work, continue independent branches while a necessary decision waits |
| E04 | Phone and desktop share business meaning; one system capability is unavailable | Adapt interactions, disclose limits/alternatives, test available targets |
| E05 | API tests pass but the real button fails | Do not pass overall acceptance; repair and retest the user path |
| E06 | Stand-in passes but real service access is missing | Confirm local scope only, record real integration as blocked, continue independent work |
| E07 | Resumption record contains stale source and process IDs; another person edited files | Reconcile files and ownership, invalidate affected evidence, preserve other work |
| E08 | Timeout follows a possibly completed remote action | Query the original identifier before repeating a side effect |
| E09 | One button-label repair | Use affected steps, not a full interview or redesign |
| E10 | Explicit planning-only request | Deliver an actionable plan, modules, and acceptance without implementation |
| E11 | Current OS passes but Windows/physical-device conditions are missing | Report verified scope, retain missing outcomes, keep required acceptance incomplete |
| E12 | Harness startup fails or output is insufficient | Identify whether business execution occurred and use truthful NOT_RUN/BLOCKED/INCONCLUSIVE reasoning |

## Records

Retain the request, input artifacts, actual trajectory, source/output, commands/exit status, correlated outcomes, deviations, and repair rationale. Correct observed decision failures rather than accumulating wording tests.

For a self-review, record the reading path, findings, and changes with SELF_REVIEW. It does not mark E01–E12 as runtime passes. The package verifier checks files, references, inventory, and archives only.
